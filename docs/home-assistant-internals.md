# Home Assistant internals this fork depends on

Everything here was read from the Home Assistant source or measured on a running instance
(Core 2026.9.1). It is written down because each item is either invisible from the documentation or
actively misleading, and every one of them cost a debugging round.

Keep this current when the fork changes.

---

## 1. The template integration's internals move between releases

The platform builds on `homeassistant.components.template`, which is not a public API. Two names
changed in 2026.9 alone:

| Name | Release | What to use |
| --- | --- | --- |
| `make_template_entity_base_schema` | renamed by core PR #178762 | `make_template_entity_common_schema`, with a `try`/`except ImportError` fallback |
| `validate_template_scripts` | removed from `template.helpers` | import defensively, skip the call when absent |

The surviving names this platform relies on are `async_create_template_tracking_entities` and
`TemplateEntity`. Expect this list to grow. `hass-template-climate` carries the same shim, so when it
breaks, look there for the fix first.

### `check_config` will not catch it

A custom component that cannot import still passes `check_config`, because Home Assistant scans
`custom_components/` at startup only. The single warning reads *"Integration 'humidifier_template'
not found"*, which looks like a typo rather than a broken import. The honest gate is a real import in
a fresh interpreter:

```bash
docker exec homeassistant python3 -c \
  "import sys; sys.path.insert(0, '/config'); import importlib; \
   importlib.import_module('custom_components.humidifier_template.humidifier')"
```

Fix one import error, run it again, and expect another.

## 2. Entity attributes: what core does and does not police

`HumidifierEntity.state_attributes` publishes the action like this:

```python
if self.action is not None:
    data[ATTR_ACTION] = self.action if self.is_on else HumidifierAction.OFF
```

Two consequences the `error` action depends on:

- **No enum validation.** Whatever `self.action` holds is serialised, so a platform may publish a
  value outside `HumidifierAction`.
- **Only while the entity is on.** When it is off, core forces `off`. So an extended value is
  visible exactly when the device is switched on and unable to work, which is the case worth
  showing, and a user-switched-off entity still reads Off.

## 3. Attribute values are translated from the platform first

`compute_attribute_display.ts` resolves an attribute value through four lookups, in order:

1. `component.<platform>.entity.<domain>.<translation_key>.state_attributes.<attr>.state.<value>`
2. `component.<domain>.entity_component.<device_class>.state_attributes.<attr>.state.<value>`
3. `component.<domain>.entity_component._.state_attributes.<attr>.state.<value>`
4. the raw value

**The platform's own namespace wins.** That is what lets this integration render `error` as *Error*
rather than a lowercase fallback, without touching core: set a `translation_key` and ship
`translations/en.json`.

Two traps come with it:

- **`_attr_translation_key` must be set on the instance, not the class.** `Entity`'s metaclass turns
  every `_attr_` name into a property, so a class-level assignment never reaches the entity.
- **The entity registry records `translation_key` when the entry is created.** Existing entities keep
  whatever they were registered with, so delete their registry entries once after upgrading, or the
  translated values will never appear. A platform reload is not enough — it re-instantiates from the
  module already in memory. A Core restart is required.

Verify what the frontend actually has:

```
frontend/get_translations {language: en, category: entity, integration: humidifier_template}
```

## 4. Legacy `*_template` option names are accepted and ignored

The platform schema accepts `icon_template`, `entity_picture_template` and `availability_template`,
but the modern template entity base reads `icon`, `picture` and `availability`, and this platform
never wired the long spellings. Left alone they are silently dropped: an `icon_template` simply never
renders, with no warning.

This fork maps the legacy names onto the modern ones before the entity is created, so both spellings
work. If you add another option, check whether the base already owns it under a shorter name.

## 5. Generated dashboards choose one feature per tile, from a fixed list

The built-in **Climate**, **Home** and **Areas** pages are not dashboards. They are frontend-shipped
panels (`get_panels` returns `component_name: "climate"`, `config: null`), generated by view
strategies. Every tile comes from `computeAreaTileCardConfig`, which picks **exactly one** feature:

```
light-brightness -> cover-open-close -> target-temperature -> fan-speed -> alarm-modes -> lock-commands
```

There is no humidity entry, so a humidifier tile gets no control. Nothing an integration reports
changes this: the decision is taken in the frontend.

### The seam

`get-strategy.ts` resolves a built-in strategy as

```ts
await STRATEGIES[configType][strategyType]();
return customElements.get(`${strategyType}-${configType}-strategy`);
```

and then calls `strategy.generate(config, hass)`. The lookup happens on **every** regeneration, so
wrapping that static method is stable rather than a patch of private state. That is what
`frontend/humidity-tile-buttons.js` does.

### A custom feature's element tag is the type minus `custom:`

`create-element-base.ts` does `_getCustomTag(type)` → `stripCustomPrefix(type)` →
`customElements.get(tag)`. So `custom:humidity-number-buttons` **must** be defined as the element
`humidity-number-buttons`. Any other tag renders Home Assistant's error card, which on a narrow tile
is truncated to a red `Configuratio…` box and reads like a config mistake rather than a missing
element.

### The widgets are unit-agnostic

`ha-control-number-buttons` — the `- 20,0 °C +` control — takes a `.unit` property. The temperature
feature merely passes `unit_system.temperature`. Passing `"%"` gives an identical control for
humidity. `target-humidity` exists as a built-in feature but renders a **slider**, and the buttons
widget is otherwise wired only to `numeric-input`, which accepts `number` and `input_number` only.

## 6. Shipping frontend assets from the integration

`hass.http.async_register_static_paths([StaticPathConfig(url, path, cache_headers=False)])` plus
`frontend.add_extra_js_url(hass, f"{url}/file.js?v={version}")` gives a module that loads on every
page load with no `configuration.yaml` entry and no copy in `www/`.

- Call it from **`async_setup_platform`**. A platform-only integration has no `configuration.yaml`
  key of its own, so `async_setup` is not guaranteed to run.
- `cache_headers=False` means the response carries ETag and Last-Modified instead of a long
  `max-age`, so replacing the file and hard-refreshing the browser picks up a change **without a
  Core restart**.
- The `?v=<manifest version>` query is belt and braces for clients that cached an older copy under a
  previous configuration.

## 7. Reading state right after a write

`.storage/core.entity_registry` on disk lags a registry write; Home Assistant flushes it later.
Reading the file straight after removing entities showed them still present, then absent, neither
matching reality. Read the live registry instead:

```
config/entity_registry/get {entity_id: ...}
```

The same delay applies to `.storage/energy` and to config entries.
